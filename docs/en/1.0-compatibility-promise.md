# intent-cli 1.0 compatibility promise

This is the compatibility commitment for the `intent-cli` 1.x line. It
records the v0.11.1 surface being ledgered; it does not change that surface.
The decision is recorded in [ADR 0002](../adr/0002-one-dot-zero-compatibility-promise.md).

## What 1.0 means

From 1.0, a MINOR release may add compatible capability and a PATCH release
may correct a compatible implementation. A breaking change to a covered
surface requires the next MAJOR release, except that the documented
deprecation path below may introduce a replacement while retaining the old
surface through 1.x.

### Covered surfaces

The promise covers exactly these machine-consumed surfaces:

- command names and flag names;
- JSON field names, field semantics, and all machine-emitted `cause` values
  consumed by automation;
- exit codes;
- durable-record schemas and their allowed state transitions.

It explicitly does **not** cover prose, document layout, Markdown headings,
or unstructured diagnostic text. Human-readable diagnostics remain useful but
are not an automation API.

### Decide whether a dependency is covered

1. Is it a command/flag, a field or machine-emitted `cause` value in JSON, an exit
   code, or a durable schema/state transition? If not, it is not covered.
2. Find the entry in the [compatibility ledger](1.0-compatibility-ledger.md).
   A registered command must be present there; the guard prevents omissions.
3. Follow that entry's disposition. A dependent must not parse prose or infer
   state from an undocumented field.

Every `cause` value actually emitted in a machine-consumed JSON payload is
covered, whether or not prose currently documents that value. Coverage follows
machine emission, not the current state of human-facing documentation.

## Freeze and preview lane

The 1.0 feature set is frozen at **v0.12.0 (2026-08-05)**. This means the
surfaces recorded in the covered-surface inventory at that freeze are the
surfaces the 1.0 promise covers; a surface shipped later in the 1.x line is
not covered merely because it was released. Decision owner: the product
owner/operator (tomohisa).

A surface added after the freeze must be documented as **preview**, recorded in
the ledger with the `preview-through-1.x` disposition, and explicitly marked
preview wherever it is described. Preview is outside the 1.0 compatibility
promise: it may change or be withdrawn during 1.x and is formalised only by a
later MAJOR release (2.0 or later). To tell which kind of surface you are
reading, check its documentation marker and its ledger entry: `stable-at-1.0`
is covered, while `preview-through-1.x` is preview and not covered.

The G637 `guide workspace-layout` surface is one such preview: its emitted
herdr command text, workspace-shape inputs, and layout prose may evolve during
1.x.

## Deprecation rule

A covered surface can change only when all of the following are present:

1. a documented replacement;
2. a structured warning that automation can consume; and
3. an alias retained through the entire 1.x line.

Removal is allowed only in the next MAJOR release. G623 ships `judgment-wait`
as the stable-at-1.0 name for the generalized durable judgment record.
`operator-attention` is its `deprecate-with-alias` compatibility alias through
1.x; its machine JSON adds `deprecation_warning` naming `judgment-wait` and
`next-major`, while the durable record schema and identifiers remain unchanged.

## Pre-1.0 road

The agreed order is:

1. G611 link guard (independent);
2. G612, this promise and ledger;
3. G623, the completed aliased `operator-attention` → `judgment-wait` rename;
4. separately eligible legacy retirements, only with named migration evidence;
5. G624, herdr-only graduation and preference; then
6. 1.0 release preparation.

G624 records the operator's 2026-08-05 decision to graduate herdr-only and
prefer it because it has fewer dependencies. The original four-teams / 20
active-days in a 30-day window figure was a conservative estimate proposed by
design, not a measurement. It is therefore explicitly revised rather than
silently missed: graduation requires zero unresolved transport-caused incidents
and live evidence of fresh provisioning, restart and headless resume,
live-handoff EOF resubscribe, topology re-record and migration including the
fleet's legacy retirement, and routing recovery. Those five recovery paths are
demonstrated live. agmsg + herdr remains supported and is not retired for
distributed teams or an existing agmsg investment; neither transport is primary.

## Inventory boundary

The ledger inventories the role-pane-mapping compatibility read, runtime-state
shapes, packet-schema variants, and field aliases. Inventory is not authority
to remove any of them. A pre-1.0 retirement is valid only when its ledger row
names migration evidence; otherwise it is retained through 1.x.
