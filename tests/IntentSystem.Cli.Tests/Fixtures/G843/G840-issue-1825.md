# G840: make the two known-flaky CLI tests deterministic

## Goal

Two tests in `tests/IntentSystem.Cli.Tests/` decide their result from wall-clock time. They have failed in CI and in local full-suite runs across several units, and every failure needed a human to judge "that is the known flake, rerun it". That judgement is the cost this slice removes: a real regression in the `notify collect --wait` loop or in the live supervision fixture would be dismissed by the same reflex. Replace the wall-clock reads in `NotifyCollectCommandTests` with a virtual wait clock injected through a new production seam, and harden the polling helper in `NotifySupervisionShrinkG734Tests` so its deadline is monotonic and its failure says why. A longer sleep or a wider `InRange` bound is not an accepted fix for any criterion. An automated project-wide guard against new timing assertions is a separate follow-up unit, not part of this slice.

## Why This Slice Exists Now

- `NotifyCollectCommandTests.WaitReturnsAfterGenuineSecondWriterAppends` (child main `ba496314`, line 64) starts a background `Task.Run` that does `Thread.Sleep(100)` and then appends, times the command with a `Stopwatch`, and asserts `Assert.InRange(stopwatch.ElapsedMilliseconds, 50, 1500)` (line 81). On a loaded runner the sleep, the command start-up and the ceiling all compete for the same scheduler.
- Two sibling tests in the same file have the same defect and are more fragile: `WaitTimeoutIsExplicitNoNewEventsAndNonError` (line 86) runs a 75 ms timeout and asserts `InRange(..., 50, 1000)` (line 98), and `NonWaitMissingReaderIsNoEventsAndReturnsImmediately` (line 102) asserts `InRange(..., 0, 500)` (line 113). Repairing only line 81 moves the flake to line 98.
- `NotifySupervisionShrinkG734Tests.WaitUntilAsync` (line 704) takes its deadline from `DateTime.UtcNow` (lines 706–707), polls with `await Task.Delay(50)` (line 714), and on expiry fails with the single string `"Timed out waiting for the live supervision fixture."` (line 717). That message cannot distinguish a starved runner from a supervisor that stopped appending cycles — exactly the judgement a human makes before rerunning.
- The 2026-09-15 operator instruction is that every open issue is triaged and every unimplemented one packetized. This flake class has been re-triaged by hand repeatedly and never packetized.

## Standalone Child Issue Contract

**1. The seam.** In `src/IntentSystem.Cli/Commands/NotifyCommand.cs` (file-scoped `namespace IntentSystem.Cli.Commands;`, line 7). **The two types go at namespace scope, not inside `NotifyCommand`**; only the two factory members go inside the class:

```csharp
// NotifyCommand.cs, at NAMESPACE scope -- beside the existing role-collect
// records NotifyRoleCollectResult (line 4924) and NotifyRoleCollectReadResult
// (line 4971). Never nested in NotifyCommand: a nested type would have to be
// written NotifyCommand.StopwatchNotifyRoleCollectWaitClock at every use site.
internal interface INotifyRoleCollectWaitClock
{
    long ElapsedMilliseconds { get; }
    void Sleep(TimeSpan duration);
}

internal sealed class StopwatchNotifyRoleCollectWaitClock : INotifyRoleCollectWaitClock
{
    private readonly System.Diagnostics.Stopwatch stopwatch = System.Diagnostics.Stopwatch.StartNew();
    public long ElapsedMilliseconds => stopwatch.ElapsedMilliseconds;
    public void Sleep(TimeSpan duration) => Thread.Sleep(duration);
}

internal static class NotifyCommand
{
    // The ONLY members this slice adds inside NotifyCommand. The property is
    // initialised FROM the readonly field: two separate lambdas are two
    // objects, and AC5's Assert.Same would then compare different references.
    internal static readonly Func<INotifyRoleCollectWaitClock> DefaultRoleCollectWaitClockFactory =
        static () => new StopwatchNotifyRoleCollectWaitClock();

    internal static Func<INotifyRoleCollectWaitClock> RoleCollectWaitClockFactory { get; set; }
        = DefaultRoleCollectWaitClockFactory;
    // ... existing members unchanged ...
}
```

Tests already `using IntentSystem.Cli.Commands;` (`NotifyCollectCommandTests.cs` line 4), so they write `new StopwatchNotifyRoleCollectWaitClock()` unqualified. The default is byte-for-byte today's behaviour: a `Stopwatch` started at construction, where `Stopwatch.StartNew()` ran before, and `Thread.Sleep`.

The loop changes at exactly three statements. Line numbers are base `ba496314`; members added above them shift them in the head file, so compare hunks by content:

- line **1149** `var stopwatch = options.Wait ? System.Diagnostics.Stopwatch.StartNew() : null;` becomes `var waitClock = options.Wait ? RoleCollectWaitClockFactory() : null;`
- line **1211** `var elapsedMilliseconds = stopwatch!.ElapsedMilliseconds;` becomes `var elapsedMilliseconds = waitClock!.ElapsedMilliseconds;` (**not** 1209, the closing brace of the non-wait `return 0;` block)
- line **1228** `Thread.Sleep((int)Math.Min(RoleCollectPollMilliseconds, remainingMilliseconds));` becomes `waitClock!.Sleep(TimeSpan.FromMilliseconds(Math.Min(RoleCollectPollMilliseconds, remainingMilliseconds)));`

The factory is invoked **only** when `options.Wait` is true, at most once per invocation. The loop still reads before it ever sleeps, and re-resolves the reader path on every pass.

**2. Why production must change, and why this is the smallest change.** The behaviour under test is "the bounded wait re-reads the reader and returns events a second writer appended after the first read came back empty". Today it is observable only as elapsed time, because the loop owns its clock and its sleep as locals, and no existing seam reaches the collect path (`NotifySupervisor.Delay` and `NotifySuperviseInstallCommand.Delay` belong to the supervisor loops, `NotifySupervisionEventMonitor.Delay` to the event monitor). A public API change is disproportionate, and a clock abstraction threaded through `CliContext` touches every command. One internal factory returning a two-member interface matches `AutomationStalledWorkCommand.*Factory` in shape and `NotifySupervisor.Delay` in intent, makes both the elapsed reading and the sleep observable, and lets the test *cause* the second writer's append at a chosen pass — the technique `NotifyEventSupervisionG751Tests` lines 206–215 already uses.

**3. What each rewritten test proves.**

- `WaitReturnsAfterGenuineSecondWriterAppends`: with `--wait --timeout-ms 2000`, the first read returns no events, a second writer appends during exactly one poll pass, and the command returns `outcome: "events"`, `timed_out: false` and exactly the appended unit. It does **not** prove the command took at least 50 ms, and it does not prove concurrent-append safety. The old `Task.Run` plus `Thread.Sleep(100)` against a 2000 ms timeout produced no interleaving either, so nothing is lost; `NotifyEventWriter` concurrent-append safety has no test today and is out of scope. Say so in the test's doc comment.
- `WaitTimeoutIsExplicitNoNewEventsAndNonError`: with an empty reader and `--timeout-ms 70`, the loop sleeps exactly 25 ms, 25 ms, then **20 ms**, accumulates exactly 70 ms of virtual time, and returns `outcome` and `cause` `no-new-events`, `timed_out: true`, exit code 0, no events.

  **Why 70, not 75.** The loop computes `remaining = timeout - elapsed`, exits when `remaining <= 0`, and sleeps `Math.Min(25, remaining)`. At any multiple of 25 the last `remaining` is exactly 25, so clamped and unclamped sleeps coincide — 75 traces `[25, 25, 25]` either way and the clamp is unobservable. At 70 the third pass has `remaining = 20`: only the clamp produces the 20 ms sleep and the 70 ms total; without it the run traces `[25, 25, 25]` and overruns its declared bound to 75. The literal is load-bearing.
- `NonWaitMissingReaderIsNoEventsAndReturnsImmediately`: without `--wait`, the factory is never invoked and no sleep occurs. That is strictly stronger than "it finished within 500 ms", which a 400 ms sleep would satisfy.

**4. The virtual clock.** A private fake in `NotifyCollectCommandTests` implements `INotifyRoleCollectWaitClock` with a `long` that advances by exactly the requested duration on each `Sleep`, records each requested `TimeSpan`, calls an optional `Action<int>` with the 1-based pass number, and counts constructions. It exposes its accumulated time as `VirtualElapsedMilliseconds` and implements the interface's `ElapsedMilliseconds` explicitly. The class constructor installs it into `NotifyCommand.RoleCollectWaitClockFactory`; `Dispose` restores `NotifyCommand.DefaultRoleCollectWaitClockFactory`, even when a test throws. No real time passes in any of the three tests.

**5. The G734 helper.** `WaitUntilAsync` is rewritten in place. Neither call site's `TimeSpan.FromSeconds(10)` changes.

- The deadline is monotonic — `var stopwatch = Stopwatch.StartNew();` — never `DateTime.UtcNow`, so an NTP step cannot shorten or extend the wait.
- A predicate that throws is treated as "not yet true" and retried until the deadline; the last exception is carried into the failure message. Reading a JSONL file another process is appending to can fail transiently, which today surfaces as an unrelated `IOException`.
- On expiry the message names the caller (`[CallerArgumentExpression]` on the predicate, or a `description` parameter), the elapsed monotonic milliseconds, the poll-pass count, the last predicate exception, and — through a `Func<string>` diagnostics provider built from `DescribeLiveFixture` (AC6) — the supervisor process state and the `cycles.jsonl` line count and last line. A reader of a CI failure must be able to tell "the runner was starved" from "the supervisor stopped appending" without rerunning.
- The message is built in **one interpolated string literal assigned to a local**, and that local is passed whole to the assertion:

  ```csharp
  var diagnostic = $"{description}: timed out; elapsed_ms={stopwatch.ElapsedMilliseconds}; passes={passes}; last_error={lastError?.Message ?? "<none>"}; {diagnostics?.Invoke() ?? "<no fixture diagnostics>"}";
  Assert.Fail(diagnostic);
  ```

  Reading the clock inside the assertion call (base line 717's inline shape) is not used.
- The helper asserts no elapsed-time bound, and neither call site gains one.
- The Release-DLL assertion at line 521 keeps its hard failure but its message names the build command that produces the DLL, so that failure is never mistaken for the flake.

The 50 ms poll quantum is not the defect and may stay.

**6. A wider timeout is not a fix.** A reviewer blocks the PR on any of: raising `1500`, `1000`, `500`, `2000` or either `10` seconds; changing AC3's `70`, above all to a multiple of 25 (mutation 3 would then survive); widening any `InRange`; a retry attribute, a rerun-on-failure wrapper, or a `[Trait]` that excludes these tests from the default run; turning an assertion into a warning; raising `RoleCollectPollMilliseconds`; or changing `Thread.Sleep(100)` at line 68 to another value instead of deleting it. `using System.Diagnostics;` is removed from `NotifyCollectCommandTests.cs` line 1.
